# T31 群组接线记录

## 已实现：群消息编解码

群子流沿用冻结的 `/asl/group/1.0.0`、4 字节大端长度前缀和确定性 CBOR `group-envelope`。收发只接受群 envelope；整帧上限 256 KiB，envelope 内的 MLS 密文上限 64 KiB。默认不注册群子流；显式回环构造器例外。编解码本身不认证身份、不授权群成员、不匹配回复。

`GroupPacket` 对操作 `1` 内的 `group-membership` 进行二次确定性 CBOR 校验，限制请求和回复种类、完全匹配群 ID、请求 ID、预期 epoch 和邀请 ID。网络 codec 只检查外层，传输适配器和 Core 分别检查消息及各自的连接、待决请求绑定。OpenMLS 适配器核验普通 KeyPackage、单收件项 Welcome、解密后的群 ID/epoch/套件及本机叶子，并检查 Application/Commit 是相符的 MLS 私有消息。同步绑定由 MLS exporter 派生，不发送原始 epoch authenticator。完整消息表见 [协议](03-protocol.md#群子流)。

MLS 应用明文通过 `group-application` 校验，只复用既有 Query、Answer、Offer、FetchRequest 和 FetchGrant。没有自由文本、未知字节载荷或嵌套群 envelope；外层 CBOR 字段和值不变。FetchRequest 只能由当前 `active` 且成员 epoch 精确匹配的房间成员发起；FetchGrant 使用原群应用外层消息 ID 关联请求，内部 Grant 的消息 ID 仍保持独立。

集成夹具使用固定 OpenMLS 0.9.2、RustCrypto 0.6.0 和测试身份，真实执行 KeyPackage、Welcome、应用消息认证与解密、移除提交，检查被移除成员不能读取下一 epoch 的消息。夹具的 BasicCredential 不等于 ASL 链身份；测试并不验收实际群邀请、持久化、成员授权、生产子进程或公网。

## 已实现：本机状态读写

SQLite v12 支持在同一事务暂存 `needs_sync` 房间与 MLS 状态记录，存放完整 32 字节线上 ID、唯一的本地 `GroupId(Id128)` 及不透明密封状态。单纯暂存不写成员行、不重写授权 ID，也不自动升级旧群。读取按完整线上 ID 精确匹配。

Windows 本机适配复用 OpenMLS 的内存存储与现有 DPAPI，密封快照绑定本机房间 ID、完整线上 ID、当前设备、版本与 MLS epoch。恢复会检查绑定和 OpenMLS 组状态；快照不属于身份迁移包。SQLite 持久化与 DPAPI 恢复各有定向测试，真实 OpenMLS 夹具用恢复后的接收方处理应用消息及移除提交。Core 已调用这些接口进行本机建群、入组和只读对账，不恢复或激活群权限。

## 已实现：MLS 身份与候选事务

MLS 1.0 使用 `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`。Core 带独立随机 MLS 签名密钥，严禁把传输私钥作为 MLS 签名密钥使用。ASL BasicCredential 内容为 `signature65 || canonical_device_certificate_cbor`；根签名的预映像是 `ASL-MLS-LEAF-v1\0 || wire_group_id[32] || mls_signing_public_key[32] || canonical_device_certificate_cbor`。检查群 ID、公钥编码和当前 ASL 证书。通过已有链解析器核对活动身份根、已验证设备目录和证书有效期；直接来源还须匹配当前认证连接中精确的 Hello 证书。同 Agent 的其他设备、过期/被替换证书和其他房间均不可复用该叶子。签名绑定只证明身份根授权该公钥；MLS 自身仍须验证该叶子或消息的签名和密钥持有关系，链证据的新鲜度沿用现有解析器规则。

SQLite `BEGIN IMMEDIATE` 比较本机/线上群 ID、快照版本、MLS epoch、成员授权 epoch 和全局权限版本，一起提交候选快照、成员投影和群事件。应用消息用群 ID、认证发送设备和 MLS 明文的消息 ID 去重，不信任外层消息 ID；提交事件用群 ID、基础 epoch 和已验证 MLS 数据去重。更新 ratchet 不增加成员授权 epoch，候选成员变化也不会使本机房间从 `needs_sync` 切为 `active`；后续只有实际授权成员或可用状态变化才推进成员授权 epoch 及全局权限版本。事件写入 7 天期限，启用回环群组的 Core 在启动时和之后每 30 秒分批清理到期密文及关联同步记录。清理不改变 MLS 快照、成员投影或同步预算，也不承诺擦除磁盘和备份中的旧副本。生产 Core 仍需在提交之前重新核对本机权限与链证据，提交失败时丢弃候选，成功后才允许交付明文或排队发送。

## 待实现：生产权限与投递

- 继续在发方 KeyPackage 和所有 Add/Update/Commit 的叶子上核对当前链状态。重启对账之后还要核对同步进度和当前权限，不能直接启用。过期、撤销和换设备需要 MLS 叶子更新或移除；不得仅删 SQL 成员行却继续用旧 MLS epoch 发信。移除与迁移不会复制旧 ratchet，也不会将群成员升级为联系人。
- 上游 `openmls_sqlite_storage` 0.3.0 的 `rusqlite` 0.37 与本项目锁定的 0.43 各自链接 SQLite，不能直接同时接入。继续使用每房间独立的内存 provider，并将密封后的候选状态与成员投影用同一个 SQLite 事务提交。

## 已实现：入站邀请本机状态

SQLite v13 记录完整线上群 ID、邀请 ID、基础 epoch、邀请方及本机目标的 AgentId 和 PeerId、短期有效期。邀请最多有效 5 分钟；同 AgentId 的不同设备共享 24 小时 1 次额度，另有本机每小时 20 次、同时未结 5 条上限。拒绝、过期和完成不退还提示额度；过期清理会移除密封包，保留 24 小时内的提示历史。启用回环群组时，Core 启动及运行期间都会清理过期邀请。群邀请不带任何自由文本。

Windows DPAPI 适配只持久化单次 KeyPackage 和对应 MLS 签名密钥，绑定该邀请元组、请求 ID 与包引用，可重建同一请求和新的候选 provider。审批先持久化才可发送，同一线上群最多一个获批的待加入包；启动后可按本机身份及设备发现尚未过期的审批。SQLite 原子消费审批、关闭同群其余邀请、创建新房间并写入冻结快照和已验证的成员投影；失败统一回滚。房间保持 `needs_sync`，不修改权限版本。GUI 同意操作和网络入口尚未接入。

收方 Core 以当前认证连接确定邀请者，只接受指向本机 AgentId 与设备的 Invite；重复邀请不会创建新提示。审批入口仅供本机用户决定使用，先保存一次性包再允许准备请求。收件、审批、恢复包都在 SQLite 中核对双方链状态和设备证书。重试只恢复原请求；旧开发加入包缺少必需能力时不可重用。恢复清单不触发发送。

## 已实现：出站邀请与 Welcome 本机事务

SQLite v14 先记录本机创建者设备、完整群 ID、基础 epoch、邀请 ID、目标 AgentId/PeerId 与最多 5 分钟的时效。全机最多保留 64 份出站记录；同一群/epoch/设备只保存一个邀请。添加必须由该创建者提交，投影变化只允许新增指定目标。候选快照、成员投影、MLS 提交事件、原请求 ID、KeyPackage 消费标记及 Welcome 密文字节在同一事务落盘。消费标记单独保留到经验证的 KeyPackage 到期，最多 4096 条；清理过期邀请不会让仍有效的一次性包重新可用。

重启或重试从 SQLite 恢复同一个回复，仅接受原 AgentId、原设备、完整群/邀请/请求 ID、基础 epoch 和包引用，且设备证书和成员仍有效。房间进入后续 epoch 不会自己改写 Welcome；移除原成员或创建者时同事务清除对应待发密文，重新入群也不能复活旧回复。该记录按邀请时效清理，不代替 Core 对认证连接、当前链证据和本机状态的复核。存储调用仅支持 `needs_sync` 阶段，不启用群权限，也不向网络发送任何内容。

Windows 本机夹具验证发方通过真实 OpenMLS 生成 Commit 与 Welcome、封存快照、重开 SQLite、恢复发方状态并用原 Welcome 让收方入群，双方对 epoch 的认证结果一致。SQLite 用例覆盖 v13 升级、写入失败回滚、请求错配、撤销与移除、邀请过期后包仍不可复用。链身份行用合成数据，不验证真实链 RPC、发方 Core、GUI 或公网；[发方存储验证](plan-validation.md#2026-11-20-t31发方邀请与-welcome-事务)。

## 已实现：Core 本机建群、定向加人、入群与对账

Core 为本机新群生成随机创建者承诺，OpenMLS 和 SQLite 使用由承诺派生的同一 32 字节线上 ID。Core 处理已获本机批准的 Welcome 时，核对创建者承诺、MLS 签名者、认证连接的精确 Hello 设备证书、本机叶及全部成员。全部通过才允许 SQLite 在同一事务再次比较设备和链状态、消费审批并保存房间。缺少承诺或必需能力的旧开发数据不能进入该流程。

发方 Core 只为当前认证连接上的指定设备准备定向邀请，先落盘再返回 Invite。处理 KeyPackage 时，核对认证连接的精确 Hello 证书和房间创建者，恢复独立候选，验证新增后的成员；同一事务复核房间版本和成员链状态，写入 Commit、快照、成员投影和 Welcome。原设备重试同一请求时，从同一 SQLite 快照比较当前房间和证书，也只取回原 Welcome。该 Core 接口不直接向网络发包。

重启后只读对账检查 DPAPI 快照、MLS 成员、SQLite 投影、当前设备和链证据。目录不能低于 Core 已知的 DHT 或认证连接历史；可信调用方可用同一设备证书的更新签名目录续期，不接受回退。对账成功不会改变 `needs_sync`，不证明已追上远端最新 epoch，也不产生联系人或文件权限。[本轮验证范围](plan-validation.md#2026-11-20-t31core-定向邀请add-和-welcome-重试)。

## 已实现：回环群子流与入群请求绑定

显式启用的本机回环传输和 Net IPC 复用已有连接、请求超时与有界句柄表。Net 把回复与原子流、认证连接和消息关联；送入 Core 的每次请求凭据独立于线上消息 ID。入站回复使用原连接上的单次 IPC 句柄，不能借其他协议或另一连接送出。回环模式不允许切换 LAN/公网策略，也不允许中继。默认生产 Net 子进程不协商群子流。

Core 群驱动仅处理 Invite、KeyPackage 和对应回复。持久化后未能入队的 Invite 可以显式重试，不换邀请 ID、不延长期限。Invite 先保存后提示，只回复结构化 Receipt，不表示本机同意。获批 KeyPackage 只有在成功交给 Net 队列后才登记待决记录；它绑定当前准入连接、原邀请及设备、完整线上群 ID、原始请求、单次发送凭据和本机房间信息。最多五条待决记录；超时、断开或对应请求失败解除待决绑定，但不消耗持久审批。重试只使用原 KeyPackage 和新发送凭据，迟到、错连接或重复 Welcome 不能再次入群。Welcome 通过匹配后仍须经过完整 MLS/SQLite 检查。

期限只在本机流转，不改线上协议。Net 将 Core 的出队期限换为单调时钟期限，协商后仍用同一截止时间限制写请求、关闭发送端、读回复和接收完成事件。入站以锁定版本 `libp2p-request-response 0.30.0` 在协商完成后克隆子流 codec 的时点为起点，不晚于 libp2p 自身工作计时器；读帧、Net 回复句柄、写回复及关闭发送端共用该期限。转发到 Core 只公布当时剩余时间，不从转发点续期；Core 继续用本机系统时间检查 IPC 到期。已经完整交给传输层的请求属于在途：即使本机关闭发送端超时，对端仍可能读到完整帧并处理，超时不等于远端没有提交。发方先持久保存 Welcome，符合条件的重试只取回原回复，不重复 Add。

## 已实现：正式进程中的回环群组与本机审批

Windows Core 启动时经私有前导把 `loopback_groups` 交给 Net。该选项默认关闭；显式开启后仍不能改用 LAN、公网或中继。Supervisor 用独立路径处理群子流，不把群帧、回复句柄或审批入口交给通用 Agent、MCP 或 Worker。断开和请求失败沿用现有待决清理；房间仍为 `needs_sync`。

配置位于 `ASL_HOME` 下的 `state/network-settings-v1.json`。使用 `version: 1`、`address_scope: "loopback_only"`、`loopback_groups: true`、空 `relay_addresses`；需接受连接的节点再启用 `listen_on_interfaces` 并设置自己的 `tcp_port`、`quic_port`。启动 `asl-core --groups` 时必须使用本机交互终端。`peers` 显示本机身份和已准入连接；按需要用 `dial <ip:port> <PeerId>` 连接另一回环节点。`create` 建群，`invite <room-id> <connection-id>` 定向邀请，`list` 显示当前设备的待审批和已审批邀请，`room <room-id>` 查看是否已落盘及当前 epoch。`approve <invite-id>` 持久保存审批并尝试发送一次；失败或重启后由本机操作员用 `retry <invite-id>` 重试。`reject <invite-id>` 只关闭尚未批准的邀请，不能删除已有加入包：对端可能已经提交 Add。查看恢复清单不会发送。双方仍需要可验证的链身份和设备目录。

启用后，Core 至多缓存 128 个 Agent 的已验证签名设备目录，来源限成功的已准入 Hello 证明或已经过签名与链核验的 DHT 目录，不采用 Welcome 自带的材料。缓存可跨断开使用，不跨 Core 重启；每次仍重新核对时效、链状态、目录历史和精确设备证书。尚未观察到某成员的新鲜目录时拒绝 Welcome，保留原审批以便先取得证据、再显式重试。建群、收发受限邀请和提交 Welcome 不再依赖文件传输预先登记设备；设备登记与对应群事务一起写入，不授予联系人或文件访问权限。超出提示额度的邀请不登记设备。新房间和成员变化后的房间先进入 `needs_sync`，只有后续状态机证据满足条件才可转为 `active`。

Core 定期以及收到有效链刷新时，由独立线程读取 `ASL_HOME/identity/device-directory.cbor` 中的新签名封装，主进程沿用原 Hello 的精确设备证书。更新必须通过签名、当前链承诺、有效期和已观察版本检查。无效更新不覆盖仍有效的目录；确认文件缺失或目录到期即暂停准入并关闭连接。相同 Agent 的其他设备若提供较新有效目录，已观察到的版本不会随连接关闭而丢失。仅更换文件不能恢复失效的链证据；远端会话仍受原准入期限约束，必要时重新握手。此路径不自动签发目录、不发布到 DHT，也不负责换发设备证书。

## 已实现：加入提交的本机同步历史

SQLite v15 将新 Add 的基础与下一 epoch 的 MLS exporter 绑定、短期有效期和精确密文事件关联。同步记录与候选快照、成员投影、包消费标记和原 Welcome 一起落盘；失败全部回滚。DPAPI 快照 v2 保留最新至多 256 个连续提交的摘要；摘要绑定本机及线上组标识、保存设备、提交签名设备、基础 epoch、两侧 exporter、有效期和精确密文。v1 快照仍可恢复，历史为空；既有事件不回填为可同步记录。

SQLite 读取仅返回距离本机 head 不超过 256 个 epoch、未超过本机 7 天期限且到 head 连续的记录。读取到记录本身不授予传输权限。

## 已实现：回环加入提交补齐

启用回环群组后，Core 在入群完成时尝试同步，并定期从本机暂停房间及当前已知成员连接中轮流选取同步对象。每轮绑定一个连接和一个群，一次应用一个提交；断开、回复超时、错误分支或缺少身份材料会停止该轮，不跳过 epoch。服务端只向当前已核验的群成员回复，在同一个 SQLite 读事务中从请求的基础 epoch exporter 校验到本机密封 head，逐条核对密封摘要；任何一步损坏或过期都不返回该后缀的第一条。接收端分别核对转发设备与基础 epoch 的 OpenMLS 签名者，只应用创建者签名的单个有效内联成员变更（Add 或 Remove）。应用后把新快照、成员投影及本机同步记录原子提交。

DPAPI 快照 v3 在同一候选事务中保存房间累计拉取的提交数，上限 256。断线、换来源、重启、历史窗口滚动或 `AtHead` 都不重置。旧 v2 快照无法区分本地产生和拉取的记录，首个新同步按现有历史长度保守扣除。预算用尽后不会开启新的自动同步；须通过新的定向邀请和本机审批恢复。

`AtHead` 只表示该对端的当前视图一致，不恢复群权限。同步不拉取缺失的设备目录，不处理独立 Update。同步完成本身不赋予权限；状态机必须另行满足 `active` 条件，期间房间和群资源保持 `needs_sync`。公网、LAN 和中继均未开放。

### 定向入群与有限同步：剩余接线约束

- 邀请只发往经认证且明确指定的 `AgentId`、`PeerId`。记录关联的群 ID、随机邀请 ID、当前基础 epoch、签发方和短期有效期。本机接受前不生成或发送 KeyPackage；邀请本身不带成员表、加入密钥或自由文本，不授予资源访问。
- Core 每 5 分钟自动续签本机设备目录封装，SQLite 持久保存独立于链 registry sequence 的发布序号。续签必须重新验证当前链身份、目录 commitment、全部设备证书和本机精确设备；缺少目录文件或链证据过期时不续签。续签只供本机身份准入与直连身份证明使用，不代表已发布到 DHT。GUI 仍需沿用本机审批和显式重试语义。
- Core 处理成员提交时不得在同一 Commit 中移除一片叶子并用同一 PeerId 立即添加新叶子。离开与重新入群必须是独立的状态转换，确保 SQL 投影观察到移除并清除旧 Welcome。
- 超预算、断档和分支冲突不能在同步中跳过 epoch；重新审批是单独的恢复路径，不延续旧的群授权或同步记录。
- 移除必须区分基础 epoch 的成员身份与当前授权。先在原 MLS 树中验证签名，转发者、签名者和所有保留成员仍须通过当前链和设备校验；被移除叶子不应因已经撤销或过期而阻塞移除，也不得获得新的应用投递或文件权限。提交只移除一个指定叶子，不顺带添加、更新其他叶子或改变创建者承诺。
- 权限激活单独处理：只有本机已落盘、已对账的房间视图与符合群策略的新鲜证据才能进入候选；任一普通成员的 `AtHead` 不能证明全群最新。激活后也必须在每次实际授权时重判成员与版本，不能把曾经对齐或链上身份有效等同于当前群授权。
- 不得把编解码成功当作入群，所有群数据都不发布到 DHT。

## 已实现：回环成员移除与同房间重入

在本机控制台运行 `room <room-id>` 查看保存的成员设备；`remove <room-id> <base58-peer-id>` 只能由房间的原创建者设备执行，不要求目标在线，不能移除自己。SQLite 在同一事务写入新快照、投影和同步历史并作废目标的旧 Welcome。保留成员仍通过已有子流补齐；已经应用移除的节点不会向目标继续提供补齐。尚未同步的节点不知晓最新成员状态；没有回复也不能作为已被移除的证明。

只有已确定的移除目标不需要当前有效性。基础树与本机投影须匹配，Commit 必须由其中的创建者签名，转发设备及其余成员继续通过链和证书检查。合并后只减少目标叶子，保留叶子的证书和签名公钥不变，允许 OpenMLS 正常轮换创建者路径的加密公钥。如果目标与仍在群内的设备共用目录，而过期证书仍在这个目录里，须先取得已更新的链绑定目录；不会放宽目录准入。

重新入群由原创建者发送更高基础 epoch 的新定向邀请，在 `list` 中标记 `kind: "rejoin"`，仍然受邀请提示限额，须本机再次 `approve`。同一设备若还在创建者的树中，先独立移除，再邀请添加；不同设备使用各自的新 KeyPackage。收方保留本机房间 ID 和名称，从独立 Welcome 安装新快照；不把这个操作当作旧提交链的连续同步。SQLite 比较发送时的快照版本并原子消费审批、替换成员投影、清除旧同步记录。初次入群和重入都在落盘前重新核对原请求期限、邀请、认证连接和成员身份；处理中到期即回滚。只有新的有效 Welcome 可重新开始补齐预算；旧邀请、重复 Welcome 或落后的 epoch 都不行。

这段移除流程本身只推进成员 epoch 并把房间退回 `needs_sync`，不沿用旧群授权。后续完整同步、创建者激活或已验证 `AtHead` 可按状态机重新进入 `active`；任何旧同意、lease 和块请求仍保持失效。

## 已实现：结构化群消息的 MLS 加解密封装

库层可将 Query、Answer、Offer 编成确定性 CBOR，再用与本机成员叶子匹配的签名密钥通过 OpenMLS 加密为群 Application 帧。接收只处理候选树的当前 epoch，MLS 验证的发送叶子必须与调用方从认证连接和已核验成员表取得的叶子一致。解密仍按原有结构校验，不接受自由文本或其他帧。外层消息 ID 只用于请求匹配；应用去重使用认证明文的 ID。

候选状态独立加载，出错即丢弃；在 SQLite 提交之前不得发送密文或交付明文。OpenMLS 封装本身不做链身份或权限判断。

## 已实现：Core 群消息本机事务

Core 在独立候选中收发准备，要求调用方指定精确房间版本；解密前核对 epoch、已认证连接的精确 Hello 证书与发送者叶子。应用和请求的有效期、设备和链证据在事务提交前复核。SQLite 同时比较快照、群成员及权限版本，检查成员对应的设备证书和链状态，并原子写入密封的新 ratchet 与密文日志。去重绑定线上群 ID、认证明文 ID 和发送设备，不采用外层请求 ID。旧 epoch、错设备、重放、版本冲突或写入失败都不返回可交付消息，也不推进持久状态。

事务成功只证明本机候选已保存，不证明远端已同步。普通成员的 `AtHead` 或传输 Receipt 不能激活房间。

## 已实现：受限回环群消息投递

启用原有回环群配置后，可信 Core 调用可以发送结构化群消息。创建者对照本机已提交的 MLS 成员表，向当前已认证的成员设备逐个入队；同一设备只选一个连接。普通成员只可向创建者发送，并且只接收创建者发来的应用消息。创建者核对自己的当前版本和成员表才接受普通成员的消息；普通成员不相互投递，也不会转发。此限制让普通成员无需凭另一普通成员的视图判断当前成员资格。

发方只加密一次，密文和发送状态落盘后再入队。SQLite 写锁保护版本及身份检查和入队边界，较新的成员变更已落盘时不按旧名单入队。同一密文的各条请求使用独立的本机传输凭据。离线不补发，不自动重试；入队不表示送达。已经入队或已发送的旧消息不能召回，接收方只处理自己的当前 epoch。

正式 Supervisor 的收方已接线：身份、成员、时效、MLS 与去重事务全部通过后，才对原请求排队回复。`room <room-id>` 可看当前 epoch 最近处理的消息类型和标识，不展示内容，不把消息交给普通 Agent。发方可在可信 Core 的本机类型化控制通道提交 Query、Answer、Offer、FetchRequest 或 FetchGrant，只报告本机入队结果，不暴露终端、MCP、Worker 或远端发送命令。回环默认关闭；普通成员互发、GUI、公网、LAN 和中继仍未开放。

## 已实现：群内文件传输授权链

客户端只在请求来源仍是当前 `active` 房间成员、设备证书与 Agent 链状态有效、本地群 ID 和成员 epoch 完全匹配时，才把结构化 FetchRequest 加密投递到已认证连接。服务端再次读取本地房间和资源快照，不接受消息内自报的群、成员或权限版本。FetchGrant 只能回到原认证连接；客户端以 MLS 外层消息 ID 关联原请求，再通过同一连接执行既有 Bulk。

SQLite v16 把下载同意和持久传输绑定到群 ID、成员 epoch、目标写入 grant、grant epoch、内容、文件名、大小及来源集合。v17 为上传同意保存认证目标设备、文件名和大小。群成员增删推进成员 epoch 并关闭旧授权，因此旧同意、旧 lease、旧块请求和重启前未完成的群传输都会失效。上传模式为 `ask` 时，FetchRequest 只得到结构化 `FetchPending`，不创建 lease；本机批准后，相同设备、内容、授权 epoch 和群 epoch 的重试才可签发一次性 FetchGrant。服务端在 FetchGrant 签发、manifest/chunk 分配、写块和完成前继续重验精确群 epoch；群 Bulk lease 不依赖消息内的群 ID，而是由服务端内存中的 lease 绑定确定，进程重启后不会沿用。

房间状态机保持两条路径：创建者只有在本地 MLS 状态、成员投影和当前设备证据一致时，才能把房间推进为 `active`；成员侧只接受创建者设备通过已验证群子流回复给出的 `AtHead`。成员变化先推进 membership epoch 并关闭旧授权。创建者可在已提交并重新核验自己的本地成员变更后激活；其他成员在 `active` 状态也会周期性向当前已认证的创建者连接核对 head，收到提交后回到 `needs_sync`，追到创建者 head 后才重新激活。不会用其他普通成员的旧视图激活房间。信任值和贡献值只参与软排序，不能替代房间成员、epoch、设备证书或本地授权。

成员侧的 head 轮询只选择已连接的房间创建者，并轮转处理房间；创建者离线时不向其他成员询问或猜测最新状态，现有群应用和群文件授权仍受本地活动状态及精确 epoch 限制。

### 回环故障排查

容器回环许可与 Windows 防火墙入站许可分别检查。测试按当前接收方配置 `asl-net.exe` 完整路径、容器 SID、实际监听端口以及均为 `127.0.0.1` 的本地和远端地址。查到生效策略中的对应规则后才拨号。接收方交接和测试退出都会释放规则，脚本退出时也会按本次运行的随机标识清理。机器策略拒绝本地规则时，测试报告失败。此操作仅在管理员验收用例中执行。[Microsoft 防火墙规则及策略优先级](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/rules)
