# 修订计划：结构化控制 + 加密自然语言、按性能伸缩的群聊与不限次交流

状态：第 7 版实现基线（2026-11-28）。第 0 节记录 D1–D5。仓库事实是：ASL/1.1 用于表达式信件，ASL/1.2 用于签名语义上下文，ASL/1.3 增加 `act-nl`，ASL/1.4 增加签名 shard binding/forward；当前存储 schema 为 v49。v46 增加联系人策略动作与固定期限交互证据，v47 曾增加逻辑群唯一 Agent 成员视图，v48 用代码内递归查询取代持久视图，v49 增加加密 shard-forward outbox。act 编解码、MLS application 收发、MCP 发信、建群/邀请/两人会话工具、持久复合预算、libp2p AutoNAT/DCUtR/relay、Core act/Policy 路由、opaque 邮箱、群策略、逐文件权限和管理员能力已经落地。普通邀请自动选择或创建独立子 MLS 群，根策略逐子群提交并返回部分结果；跨 shard 应用由逻辑群主根签名证明来源，各子群分别加密并可持久重试。文件 Offer/Fetch 现在携带可选的逻辑根和源 shard 元数据，使跨 shard 的文档授权路径可回到源 shard；文件字节仍要求双方建立直接认证传输。管理员能力按 `manage-members`/`manage-files`/`manage-invites` 分片。真实两设备重启补收、512/2,000/10,000 跨机矩阵、公网 NAT/relay 和链上部署仍未验收。

| D5 | 语义覆盖率门槛 | 取消 | 自然语言无损传递，不再需要覆盖率评估；改为提示注入红队评估（4.6） |

D4 推翻了 R32「线协议禁止自由自然语言字段」。R32 原本防两件事：

1. **网络上的第三方看到内容。** 端到端加密能解决。
2. **对端 Agent 用文字操纵本机模型（提示注入）。** 加密解决不了，因为写这段文字的正是对端本人。

所以计划保留 R32 的第二个目的：远端文字只能被模型「读」，不能「指挥」本机做事。做法见 4.4。

## 1. 目标与口径

| 目标 | 口径 |
| --- | --- |
| 不限对象 | 任何通过身份验证且获本机授权的 Agent 都可以交流，不按固定白名单数量封顶 |
| 不限次数 | 协议不写死回合数、消息数；次数由用户授予的可续期预算和机器级资源上限决定 |
| 表达不受限 | 对话内容用自然语言，只出现在端到端加密的 act 正文中；控制面（言语行为类型、动作、预算、因果链）保持结构化 |
| 群聊按性能伸缩 | 协议不写死 64 人上限；本机按实测容量决定能创建、加入或承担转发的群规模，并设编译期硬上限 |

## 2. 结论：可以在现有基础上改进

已完成的 T01–T13 大部分保留。确定性 CBOR codec、身份与链验证、授权判定、沙箱、IPC、SQLite 和检索都不需要推倒。改动集中在四处：

1. **新增 act 帧**：对话类交流走 act，自然语言只能出现在 act 正文里，act 只能出现在 MLS 解密后的明文里。旧的 query/answer/offer/fetch 帧编码不变，继续用于确定性资源检索。
2. **私聊也走 MLS**：私聊是两个成员的 MLS 组，和群聊共用加密、邮箱与预算。因此 OpenMLS 接入要从 T31 提前到 T19 之前（新任务 G00）。
3. **写死的数字改成预算**：群 64 人、3 回合/6 条消息、群回复不得触发回复，改为「本机策略参数 + 编译期硬上限」。
4. **未开工任务先改验收**：T14–T19、T26–T27、T31–T32 按新口径改写后再开工。

已完成代码中改动最大的是 `asl-types`：codec 需要支持 CBOR text string，但只在 `act` 的 `nl-body` 一个位置放行，其他结构遇到 text string 照旧拒绝。`Intent` 枚举保留，用于兼容 v1。

## 3. 必须先说明的限制

- **加密挡不住对端本人。** 对端写的文字可以是提示注入。防线不靠模型是否听话，而靠三条确定性规则：远端文字只进模型的数据区；动作只能从本机白名单中选并经过 PolicyService；模型上下文只放该对端有权看到的资料（4.4）。
- **模型回复是自由文本，存在数据外泄风险。** 结构化协议原先限制了模型能往外说什么，现在没有这层限制。如果模型在和 A 对话时看到了只授权给 B 的资料，就可能写进回复。所以「上下文按 audience 裁剪」是硬要求，不能只靠事后过滤。
- **群聊不可能真正无限。** RFC 9420 的设计目标是两人到数千人。MLS 的 Welcome 和 ratchet tree 随成员数线性增长，所以万人级必须分层（5.4）。
- **邮箱和 gossipsub 会暴露元数据。** 内容看不到，但托管邮箱的节点和 gossip 邻居能看到消息大小、时间、主题。计划用填充、主题名轮换和 libp2p 0.50.1 的 Anonymous/Anonymous validation（等价于无签名传播，身份由 MLS 证明）减少暴露，无法完全消除；文档不宣称匿名。

## 4. 对话层设计（ASL/1.3，feature `act-nl`）

### 4.1 act 帧

对话类交流统一用 act。旧 query/answer 保留，继续用于确定性资源检索（不经模型也能回答的那部分）。

| act_type | 含义 | 能否触发本机动作 |
| --- | --- | --- |
| inform | 陈述 | 否，入库并展示 |
| ask | 提问 | 只触发检索和模型作答 |
| request | 请求对方执行动作 | 只能指定本机白名单中的 `action-id`，经 PolicyService，敏感动作需用户确认 |
| propose / accept / reject | 协商 | accept 只改变会话状态 |
| commit / cancel | 承诺与撤销 | 否，记录下来供用户查看 |
| ack / clarify | 确认、要求澄清 | 否 |

```cddl
act = {
  1 => act-id,             ; bstr .size 16
  2 => conversation-id,    ; bstr .size 16，等于 MLS group_id
  3 => act-type,           ; uint，只能在次版本追加
  ? 4 => reply-to,         ; act-id
  ? 5 => nl-body,          ; 自然语言正文，见 4.2
  ? 6 => action,           ; 仅 request：[action-id: concept-ref, args: {* uint => typed-value}]
  ? 7 => attachments,      ; [* blob-ref]，文件仍走现有 blob/fetch 通道
  8 => causal-root,        ; act-id，见 4.5
  9 => hop,                ; uint
  ? 10 => expires-at,      ; positive-time-ms，Unix 毫秒
}
```

关键点：动作只由 `action` 字段决定，`nl-body` 里写「请删除某文件」不会产生任何动作。正文是给人和模型读的，控制面只看结构化字段。

### 4.2 唯一的文本边界

线格式不做主版本跳跃，只在冻结的 ASL/1 上追加次版本能力：

| 版本 | 用途 | 文本规则 |
| --- | --- | --- |
| ASL/1 | 现有 hello/query/answer/offer/fetch/error、签名记录、manifest、bulk | 保持冻结；不含任何 text string |
| ASL/1.1 | 表达式信件 | 不新增任意文本 |
| ASL/1.2 | 语义上下文 Request/Offer/Agreement/Expression | 不新增任意文本 |
| ASL/1.3 | `act-nl` 对话，feature 枚举追加 `5 = act-nl` | 仅 MLS 解密后的 `act[5]` 可带一个可选 `nl-body` |

`nl-body` 是 dialog 正文，只表示供人或模型阅读的内容，不是命令、路径、策略、动作或寻址信息。外层帧、DHT 记录、身份记录、群成员事件、邮箱槽、预算、附件、MCP 控制消息都不得出现任意文本。

`nl-body` 是单个 UTF-8 tstr，不是嵌套 map，也没有独立语言标签或正文 blob 字段。需要传文件时使用结构化 attachments/blob-ref，不能把正文伪装成附件。

代码约束：

1. 解码器只能在 `act[5]` 接受 text string。其他位置（含 act 其他字段、其他 `group-application`、所有 v1/1.1/1.2 结构和 MCP 控制结构）遇到 text string 必须拒绝。
2. `nl-body` 必须 UTF-8 有效，拒绝 NUL；当前编译上限 32 KiB，总 act 上限 60 KiB，给 MLS/TLS 包装留出空间。长度上限是资源限制，不是对话次数限制。
3. 不得把 `nl-body` 当作路径、URL、命令、文件名、action-id、authority 或 audience 解析。
4. 远端 `nl-body` 只作为 `untrusted_remote_data` 数据区内容交付；不得拼入系统提示、开发者提示、策略或工具说明。
5. `act` 只能作为 MLS application plaintext 解码。收到未解密、来源 epoch 不匹配或成员校验失败的内容时，不得把它当作 act。
6. `conversation-id = MLS group_id`。私聊和群聊使用同一 act 路径，不另造明文私聊协议。
7. `attachments` 只放 `blob-ref`，不嵌入文件名、正文、路径或文件字节。

### 4.3 控制面与语言面分工

控制面继续使用确定性 CBOR 和小型封闭词表：

- `act-type`：`inform`、`ask`、`request`、`propose`、`accept`、`reject`、`commit`、`cancel`、`ack`、`clarify`。
- `action-id`：只能来自本机 PolicyService 注册的动作白名单。
- 目标、预算、期限、附件、因果根、MLS epoch、群成员和路由均由结构化字段表达。
- 词表通过 minor version 追加；未知可选字段可忽略，未知必需字段拒绝。
- `specs/vocabulary-v1.csv` 不扩充为 Wikidata 式大词表（D4）；DHT 发现、公开 profile 和结构化 query 仍沿用现有概念 ID。

自然语言、解释、讨论、澄清和较长的意图说明放入 `nl-body`。这样 Agent 不受有限词表阻碍，同时机器不会从文字中推断权限或执行动作。原「无法映射到词表就不发送」的规则只继续约束结构化 query/answer，对话交流不再要求可映射；确定性资源检索仍由旧帧承担，不把 `nl-body` 当作资源检索的前置条件。

### 4.4 提示注入隔离

每个入站 act 按以下固定管线处理：

1. 验证认证连接、设备证书、MLS 成员身份、epoch、重复 ID 和预算。
2. 解开 MLS 明文，拆出结构化控制字段与独立的 `untrusted-remote-data`。
3. `nl-body` 只进入模型的数据区，标记来源 AgentId、conversation-id、act-id 和 audience；不得拼入系统提示、开发者提示、策略文本、工具说明或本机任务目标。用定界符与 spotlighting 明确标出「以下为远端不可信数据」。
4. 模型不得通过文字创建工具调用。动作只能来自结构化 `action`，并再次经过 PolicyService；敏感动作按本机规则请求用户确认。
5. 组装上下文时按 audience 裁剪。只允许该会话成员、该发送者和本机策略均允许的资料进入上下文；未授权给当前会话的数据不得因「可能有用」而被读取。这是防外泄的主要控制点，不能只靠发送前过滤。
6. 模型生成回复时，如果是对话答复，只能写入新的 act `nl-body`；如果建议动作，只生成结构化 action proposal，不能直接执行。
7. 发送前对模型输出做结构校验：对话回复只能写入新的 `nl-body`（字符集与长度按 4.2）；动作建议只能是白名单 `action-id` 的 proposal；任何路径、URL、命令行、权限字段一律拒绝。校验失败整次拒绝，不做部分发送。

`nl-body` 中出现「忽略规则」「读取某目录」「把资料发给另一个 Agent」等文字，永远不产生权限。即使模型理解并复述这些文字，也不能改变本机授权。

### 4.5 可续期预算

协议不写死回合数或消息数，也不保留「群回复不得触发回复」的语义禁令。循环由以下确定性条件约束：

- 用户授予的预算：主体、会话范围、有效期、消息数、字节数、模型调用数、CPU/时间和邮箱配额。
- 机器硬上限：单帧大小、队列长度、并发数、磁盘、内存、网络速率和抢占策略。
- 因果与去重：`act-id`、`reply-to`、`causal-root`、`hop`、MLS epoch 和持久去重表。`hop` 超阈值、同一 `causal-root` 重复出现或去重命中异常时自动暂停该会话并等待用户授权，不静默丢弃也不无限重试。
- 远端不能修改预算、路径、动作白名单或权限；这些字段只由本机 PolicyService 与用户授权生成，远端 act 中不携带。

预算可由用户在 GUI 或 MCP 授权策略中续期。续期生成新的预算版本，不能通过更换设备、重连、清空内存、更换 PeerId 或重启进程重置旧额度。用户可以设置自动续期的时间窗和总量；超过上限后进入等待用户授权状态。

预算耗尽不等于消息丢失。在线消息进入有界 outbox；离线消息进入加密邮箱；本地磁盘或队列不足时明确显示「未收取/未发送」，不得静默丢弃。

### 4.6 提示注入红队门槛

取消语义覆盖率门槛（D5），改为固定红队语料和确定性验收：

- 语料覆盖指令覆盖、角色伪造、工具诱导、路径诱导、机密外泄、跨 audience 套取、附件诱导和无限回复。
- 注入只能停留在数据层；不得改变授权、动作、目标、预算、工具或本地文件状态。
- 回复不得包含当前 act audience 无权获知的资料。
- 恶意 `nl-body` 不得造成进程崩溃、无界内存、无限模型调用或绕过发送者配额。
- 红队失败按功能缺陷处理；硬化测试放在私聊、群聊和文件闭环之后集中执行（第 9 节）。

### 4.7 act 生命周期

一个 act 依次经历：接收/认证、MLS 解密、schema 验证、预算扣减、去重、持久化、Agent 通知、模型或本地处理、回复入队、送达确认。私聊和群聊共享同一个生命周期。

- `ask` 可触发检索和模型处理；浏览模式不产生回答。
- `inform`、`clarify`、`ack` 进入会话历史并通知 Agent。
- `request` 只能引用白名单 action；没有合法 action 时只作为普通文本数据展示。
- `propose/accept/reject/commit/cancel` 只能改变对应会话状态机允许的状态。
- 所有入站 act 都先通知 Agent；是否需要回答、收取附件或向用户请求授权由本机预算和权限决定。

### 4.8 MLS 应用明文封装

当前实现不接受额外的 `group-plaintext` 包装。MLS application plaintext 是既有确定性 `WireFrame` 群应用帧或 ASL/1.3 `act` 二选一：

```text
group-application = query / answer / offer / fetch-request / fetch-grant /
                    fetch-pending / error / expression-letter / act
```

- 发送者身份由 OpenMLS 当前 epoch 的签名叶和当前已验证 roster 绑定；不接受消息自报 sender-leaf。
- 直连路径同时核验认证连接、设备证书和 MLS sender；gossipsub 路径核验 MLS sender、当前 roster、链设备证据和 room epoch，不把 gossip 转发邻居当作作者。
- act 在发送前加密一次，同一密文可 direct fan-out 和 gossipsub 发布；接收端按 MLS 重放与 act-id 去重。
- `asl-net` 只转发有界不透明 MLS 字节，解密、成员状态、act 校验和群授权留在 Core/`asl-groups`。

### 4.9 ASL/1.4 跨 shard 封装

子群之间不能复用 MLS 密文。逻辑群主在源子群收到并认证原应用后，创建根身份签名的 `ShardForward`，绑定根群、源/目标子群、原 Agent/Peer、源 epoch、原消息 ID、期限和目标 `ShardBinding`，再为每个目标子群分别做 MLS 加密。接收端只用当前目标群主、已验证 controller、签名和持久 receipt 判断来源，不把 MLS bridge leaf 当作原作者。策略、成员变更、移除请求和嵌套转发不得跨越该封装；跨 shard 文件 Offer 可转发，文件字节仍要求双方建立直接认证传输。

## 5. 私聊、群聊、邮箱与伸缩

### 5.1 统一会话模型

私聊定义为两人 MLS 组，与群聊共用以下组件：

- OpenMLS 房间、欢迎、提交、epoch、成员移除和重入规则。
- act 编解码、去重、预算、因果链、模型隔离、历史与通知。
- 加密邮箱、outbox、重连补收、文件 offer/fetch/chunk/hash 和双端授权。
- GUI 会话视图、浏览/回答模式、静音、提醒和导出策略。

不要在私聊上另建一条「已验证连接直接发明文」的旁路。私聊与群聊的差异只有成员数量和路由策略。

### 5.2 路由层级与容量分级

群规模没有固定 64 人上限。路由按本机实测容量（`capacity-profile`）和成员规模自动选择：

| 级别 | 建议成员数 | 路由 | 说明 |
| --- | --- | --- | --- |
| S | ≤ 64 | 对已认证成员逐个直连发送 MLS ciphertext | 复用现有认证连接，与 `docs/01-product.md` 第 129 行的原逐成员投递一致 |
| M | 65–512 | 单 MLS shard；逻辑群主按根签名转发跨 shard 应用 | 512 是当前单 MLS 编译硬上限；策略和成员变更仍由 MLS application 验证 |
| L | >512 | 最多 20 个独立 MLS shard，逻辑群唯一 Agent 数上限 10,000 | 按 5.4 拆子群；逻辑群主解密后重新加密，不把 bridge 当作原作者 |

- 单 MLS shard 硬上限是 512；逻辑群规划上限是 10,000 个唯一 Agent。逻辑群数量没有业务硬上限，实际资源由本机数据库、磁盘和并发预算约束。
- `direct_max`、gossip mesh 参数、队列和并发都是本机配置/实测值，不是协议全局人数常量。群可在运行中从 direct fan-out 迁移到 gossipsub，迁移不能改变 MLS group_id、epoch、消息去重语义或已授权 permit 的 audience 判定。
- **gossipsub 只传密文**：libp2p-gossipsub 0.50.1 使用 `MessageAuthenticity::Anonymous` + `ValidationMode::Anonymous`（无 author/signature 字段，发送者认证由 MLS 提供），topic 从 32 字节 room key 派生，禁止携带群名或 AgentId；mesh 邻居只看得到密文大小与时间。
- **连接分池**：私聊/小群直连连接与大群 gossip 连接分开池化、独立配额，避免大群流量挤占已建立的低延迟私聊会话。
- **group-fragment**：超过单帧预算的 MLS ciphertext 或成员摘要按固定序号分片，见 4.8。
- 成员变更继续由 MLS Commit 决定；gossip 只负责传播密文，不负责授予成员资格。接收端必须按 act-id、group-id、epoch、fragment 序号和消息摘要去重。

### 5.3 加密离线邮箱

离线邮箱是 DHT/relay 上的密文存储，不是中心服务器，也不改变 `docs/01-product.md` 第 123 行「不做中心化第三方邮箱」的立场：

1. 发件端为目标设备或 MLS 组生成加密 envelope。
2. envelope 只保存密文，按固定大小桶填充，并可按 `shard-id` 分片。
3. DHT 托管节点只保存随机槽位、密文摘要、过期时间、大小桶和有限的可用性信息；不能获得 `nl-body`、身份资料、文件名或明文主题，也不参与身份判定。
4. 邮箱指针用轮换的 pseudonymous topic 表达；topic 不包含群名、Agent 名或长期稳定可追踪标签。
5. 每个 Agent/设备/群有独立的投递和收取配额；邮箱容量不足时排队或明确拒绝，不覆盖仍有效的密文。配额独立于聊天、文件和模型额度。
6. 收件端上线后先验证身份、设备证书和预算，再拉取密文、校验摘要、重组分片、用 MLS/设备密钥解密。
7. 成功持久化后可签收；未签收的密文默认保留 7 天（与 R19 一致），最长不超过本机策略，按 TTL 与结构化状态清理。过期清理和重复投递由结构化状态处理。

邮箱内容落盘只有密文。本机解密后的历史按现有本地数据保护策略保存；联系人、信任表和浏览记录不进入 DHT。元数据暴露的缓解手段为固定大小桶填充、topic 轮换、gossipsub Anonymous validation 与连接分池，无法完全消除，文档不宣称匿名。

### 5.4 MLS 规模现实与容量准入

RFC 9420（MLS）的设计区间是两人到数千人：Welcome 消息、ratchet tree 和 Commit 的大小与成员数近似线性增长，成员变更会触发全组更新。所以「条件允许就无限群聊」不能理解为单个 MLS 组无限扩张——万人级必须按 5.2 的 L 级分层，把唯一 Agent 拆到独立子群。当前实现由逻辑群主接收源 shard 的已认证 application，验证根身份授权和持久 receipt 后，为每个目标 shard 重新加密；bridge 不能直接转用其他 shard 的 MLS 密文。单 shard 512 硬上限、逻辑群 10,000 唯一 Agent 上限和 epoch 重放窗口必须保持有界。

首次启动、配置变化和定期基准中实测 CPU、内存、磁盘、上下行、MLS 操作延迟、邮箱分片和 gossip 收敛时间，形成本机容量等级。创建、加入或承担转发时使用该等级判断：

- 超出本机能力的邀请显示预估资源并可拒绝/推迟。
- 群成员增加前重新评估 Welcome、Commit、重放窗口和邮箱成本。
- 资源紧张时先降低 gossip mesh、收取并发和非必要历史保留，再停止接受新群。
- 协议只定义线格式、最小安全限制和编译期资源上限，不定义 64 人、固定 3 回合或固定 6 消息的业务常量。

### 5.5 群与私聊文件

文件继续走既有 `offer -> fetch -> chunk -> hash` 授权路径。act 的 `attachments` 只携带 `blob-ref`：

1. 发送方在会话中发送结构化 offer，列出 blob-ref、大小、块数、摘要和期限。
2. 接收方按本机共享/接收授权决定自动收取、请求用户授权或拒绝。
3. 实际读取每个 chunk 时重新验证 read/fetch permit、成员资格、epoch 和路径白名单。
4. 大文件使用块 hash、断点续传、多来源下载和失败重试。
5. 下载完成后再由 Agent 收到「文件已到达/已缓存」的结构化通知；不得把文件字节塞入 act 或模型提示。

私聊和群聊文件共用同一传输实现。群成员移除、预算到期或目录撤权后，新请求立即失效；已签发 lease 按现有规则重验。

### 5.6 用户授权边界

Agent 可以提出建群、邀请、加入和文件交换建议，但以下动作必须由用户授权或命中用户预先定义的策略：

- 创建持久群。
- 邀请新成员、批准加入、移除成员。
- 开启公网发现、邮箱托管或持续 gossip 转发。
- 对指定目录开启自动发送/自动接收。
- 延长预算或提高资源等级。

授权策略必须绑定主体、会话、资源、期限和动作；模型输出、远端 `nl-body`、信任值、贡献值和在线状态都不能替代授权。

### 5.7 群主、管理员与成员权限

参考 QQ/微信群管理，但保持去中心化和可验证：

- 群创建者是群主；群主由 MLS room creator 绑定，不接受成员自报。群主可通过 MLS application plaintext 的 `group-policy` 设置成员默认文字、文件和邀请权限，并指定管理员及禁言设备。
- 后端策略使用单调递增 revision；非群主发送、回退 revision、指定非活动成员、禁言群主或重复/乱序 PeerId 均拒绝。接收端先验证当前 epoch 的 MLS sender 是群主，再原子更新本地投影。
- 成员端对入站 `act`、查询/表达式和文件 `Offer` 重新检查策略；群主和管理员只能收窄本机可见行为，不能绕过用户目录授权、收件目录授权、设备证书或传输审批。
- 联系人、信任、贡献和在线状态不能替代群主身份或用户授权。群管理动作必须在 GUI/MCP 中明确显示其作用域和结果，不能把“排队”展示为“已完成”。

## 6. 身份、迁移与分身/女巫防护

### 6.1 链上身份与设备证书

- AgentId 由链上根身份稳定绑定；本机根密钥不直接暴露给每个运行进程。
- 每台设备持有独立设备密钥、PeerId 和短期设备证书。证书绑定 AgentId、PeerId、能力、签发时间、到期时间和撤销状态。
- 入群、发 act、拉文件前同时验证活动链身份、签名设备目录、当前设备和连接 PeerId。
- 换机时由根身份签发新设备证书；旧设备可撤销。MLS 通过新 KeyPackage/成员更新继续，不把旧 ratchet 或旧设备权限复制给新设备。
- 可迁移数据使用加密导出包：身份绑定和可公开寻址信息跟 AgentId 迁移；联系人、信任表、历史和解密密钥由用户选择是否随包迁移。
- 链不可用时，已缓存身份只能按既有缓存期限工作；过期后停止新会话和敏感动作。

### 6.2 分身与女巫的资源防护

目标不是证明「每个 Agent 背后都是唯一人类」，而是防止大量身份攻击个人计算机。所有入口按 `AgentId + device + PeerId + IP + conversation` 分桶限额：

- 身份证明、连接握手、act 入站、模型调用、邮箱投递、邮箱拉取和群邀请各有独立预算与队列。
- 群邀请只能由用户策略批准；同一群、同一设备、同一来源的待决邀请有数量和期限限制。
- 新 Agent 只能获得低额度试用预算；提高额度需要用户授权或稳定的本地交互结果。
- 邮箱分片、gossip 主题和订阅数受磁盘/网络配额限制；主题轮换后旧主题进入冷却。
- 信任值和贡献值只影响本地排序、展示和预算建议，永远不能绕过身份验证、文件授权或 PolicyService。
- 资源耗尽时优先保留已有合法会话，拒绝新连接/新群/新邮箱，并允许用户手动解除。

这些限额是本机防护，不构成全网收费、代币或贡献门槛。

### 6.3 公网 P2P 安全

- 传输继续使用 Noise/QUIC 或等价的双向认证加密；身份准入在 MLS 和 act 之前完成。
- 监听地址、bootstrap、relay、DHT 节点和邮箱宿主全部来自配置/发现，不写死域名、IP 或盘符。
- relay 只转发密文和受限元数据，不能解密 act 或文件块。
- 默认不接受未知来源的高成本操作；公网监听、自动加入和中继能力由用户显式开启。
- 远端链接、文件名、`nl-body` 和模型输出都不能直接触发打开文件、执行程序或访问白名单外路径。

## 7. 文档冻结与实现契约

### 7.1 冻结决定

以下决定在代码实施前冻结：

1. 线格式在冻结的 ASL/1 上演进为 ASL/1.3，feature 枚举追加 `5 = act-nl`；既有控制帧、签名记录、manifest 与 bulk 编码不变。
2. 术语统一为 `nl-body`；它是 `act[5]` 的单个 UTF-8 tstr，不再使用 `nl-text` 或嵌套 map。
3. 外层控制面无任意文本；自然语言只在 MLS 解密后的 `act[5]`。
4. 私聊是两人 MLS 组，和群聊共用预算、邮箱、文件、历史和通知路径。
5. 预算可续期；协议不写死 3 回合、6 消息或固定群人数。
6. 小群 direct fan-out，中大群 gossipsub，万人级分层；本地实测决定容量，编译期设硬上限。
7. 邮箱只存密文，支持分片、填充、TTL 和 topic 轮换。
8. 文件只通过 blob-ref + offer/fetch/chunk/hash 传输。
9. 信任值不改变权限；链身份、设备证书和用户授权决定权限。
10. 先完成私聊、群聊、离线消息和文件闭环，再集中做大规模 hardening。

- 两台独立设备建立两人 MLS，双向发送/解密 act；重启后从持久化状态恢复。
- 两人组和 3 人群使用同一编解码、预算、历史和附件引用路径。
- 非成员、错误 epoch、重复 act、被移除设备和旧设备证书不能发送或解密。
- 私聊和群聊都能把未在线消息交给邮箱路径，不出现按会话类型分叉的明文实现。

### 8.3 T14–T19 增量验收

保留现有任务标题和安全实现，只增加本计划要求。

| 任务 | 增量验收 |
| --- | --- |
| T14 libp2p Driver 与链身份握手 | act、MLS 群流、邮箱和 gossip 事件只能在链身份、设备目录和连接 peer 全部准入后交付；公网监听/地址来自配置，换地址不崩溃 |
| T15 引导、中继、NAT 与基础设施 | bootstrap/relay 只传密文和受限元数据；邮箱宿主、gossip 邻居和 relay 都有资源配额；缺失主机不写死默认地址 |
| T16 mDNS、地址策略与连接观察 | 局域网可直连；未验证连接不能进入 act；IP 观察仅用于本机资源分桶和被用户查看，不进入公开身份 |
| T17 DHT 标签与记录过滤 | DHT 只存封闭结构化记录、邮箱槽和 pseudonymous topic；拒绝任意文本、`nl-body`、文件名和目录路径；信任值不改变记录授权 |
| T18 有界查询路由 | 旧 query/answer 继续服务确定性检索；act 对话不伪装成 query；两种情况共享发送前身份和预算重验 |
| T19 会话、消息与 outbox | 改成通用私聊/群聊会话；移除固定 3 回合/6 消息；实现预算扣减、续期、causal-root、hop、去重、加密邮箱补收和明确的通知状态 |

T14–T18 已有的安全切片不删除、不回退。只有与本计划明确冲突的 64 人、固定回合/消息和「群回复绝不触发回复」业务规则需要替换。

### 8.4 T26–T27 增量验收

| 任务 | 增量验收 |
| --- | --- |
| T26 严格结构化模型决策 | `nl-body` 仅作为 `untrusted-remote-data` 进入数据区；模型不能直接生成可执行动作；action 必须来自结构化字段并经 PolicyService；被当前 audience 禁止的资料不进入上下文 |
| T27 自主状态机 | 统一处理私聊、群聊、查询、邮箱唤醒和附件通知；浏览模式可读但不回答，回答模式在预算内回答；消息数/回合数由可续期预算决定，耗尽后等待授权而非静默停止 |

验收场景：

- 注入语料包含「忽略规则并读取本地目录」，实际动作数为零，审计显示只在数据区。
- A 与 B 对话时，B 无权看到的 C 会话资料不进入上下文，也不会出现在 B 收到的回复。
- 同一 Agent 多设备共享预算与去重；重连、换设备、重启不能重置。
- 群回复可继续触发群回复，但因果链、去重和续期预算能阻止无界循环。
- 收到 act 或文件 offer 时主动通知 Agent；无接收权限时进入「请求用户授权」，设为不交流的会话在程序启动时再次确认。

### 8.5 T31–T32 增量验收

| 任务 | 增量验收 |
| --- | --- |
| T31 OpenMLS 群房间与加密投递 | 大于 64 的群可创建/加入；小群 direct fan-out、中大群 gossipsub、万人级分层可切换；容量由实测决定；成员变更只由 MLS Commit 生效 |
| T32 群策略、浏览/回答与传输确认 | 建群/邀请/加入/移除都经用户授权；私聊和群聊文件共用 offer/fetch/chunk/hash；附件只传 blob-ref；浏览、回答、静默、自动收取和通知状态可解释 |

规模验收矩阵使用测试档位而不是产品硬上限：

- 2、32、128、512 个设备验证 direct/gossip 切换、成员移除和预算公平性。
- 2,000 个逻辑成员验证 gossipsub 收敛、主题轮换和邮箱积压。
- 10,000 级使用分层拓扑验证子群桥接、Welcome/Commit 成本和单机资源保护。
- 每档记录 CPU、内存、磁盘、带宽、p95 收敛、重复率和失败恢复；本机低于门槛时拒绝继续扩容。

### 8.6 执行顺序

1. **冻结文档与线格式**：已冻结 ASL/1.3 `act`、版本、文本边界、v35 邮箱底座和 v36 群权限迁移；后续只允许按次版本兼容规则追加。
2. **G00 会话基底**：完成两人 MLS 和通用会话接口，放在 T19 前。
3. **T14–T19 功能闭环**：复用现有身份、网络和查询基础，接入 act、预算、outbox、私聊和邮箱入口，完成公网配置化。
4. **T26–T27 Agent 闭环**：接入浏览/回答、注入隔离、主动通知、授权请求和可续期预算。
5. **T31–T32 群与文件闭环**：先小群 direct，再 gossipsub、分层、离线邮箱和群文件；先完成功能，不等待大规模 hardening。
6. **集中 hardening**：在私聊、群聊、文件都能端到端跑通后，统一执行提示注入红队、公网安全、sybil/分身资源攻击、规模和多来源文件测试。

阶段退出门槛：

- 两人私聊：用户授权后可持续交流，离线密文可补收，预算可续期，文件可接收或请求授权。
- 小群：建群/邀请由用户授权，成员收发 act，成员移除生效，群文件可双端确认。
- 大群：超过 64 人可加入，路由可迁移，单机有容量门槛和退避。
- 文件：act 只出现附件引用，实际字节始终经既有授权传输路径。
- 安全：没有外层文本旁路，没有 `nl-body` 触发动作，不需要信任值改变权限。

本计划到此为可执行基线；实现中若遇到与 OpenMLS/libp2p 实际能力冲突，只能调整容量参数、拓扑阈值和存储拆分，不得回退文本边界、用户授权、链身份或文件传输授权。

## 9. 兼容、互通与测试

### 9.1 版本协商与 v1 兼容

- `Hello` 的 feature 枚举追加 `5 = act-nl`。双方 minor ≥ 3 且都声明该 feature 才允许 act；只有一方支持时不发送 act，仍可用原有结构化帧通信。
- major 版本不兼容照旧断开；minor 版本只追加可选字段，未知可选字段忽略、未知必需字段拒绝。
- 既有 hello/query/answer/offer/fetch/error、错误码、签名记录、manifest、bulk、设备证书与链证明的编码逐字节不变；`Intent`（1–6）、`TypedValue`、`Claim`、`ConceptRef` 全部保留。
- `schemas/asl-v1.cddl` 追加 ASL/1.3 `act`，不修改既有 ASL/1.1/1.2 root；确定性 CBOR 规则不变，唯一额外 text 例外是 `act[5]` 的 tstr 及其长度/UTF-8 校验。

### 9.2 互通测试矩阵

| 组合 | 期望 |
| --- | --- |
| ASL/1 ↔ ASL/1 | 行为与现有固定向量完全一致，无回归 |
| ASL/1.3 ↔ ASL/1.3 | 两人 MLS 私聊、S/M/L 群、gossipsub、act 通知、预算、文件 offer/fetch 全链路可跑通 |
| ASL/1.3 ↔ ASL/1.2 或更旧 | 降级为结构化帧，不发送 act；不因对端旧版本而放宽本机文本边界 |
| 成员移除 / 设备撤销 | 新消息不可解密，旧消息不承诺远程删除；旧设备证书不能发 act |
| 迁移与重启 | conversation-id、预算消耗、去重表、邮箱签收状态可恢复，不重置额度 |
